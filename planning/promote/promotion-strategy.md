## 0. 한 줄 요약

## 1. 목표 — 평가 기준에 맞춘 두 축

| 축 | 평가 기준 | 홍보에서의 목표 | 확인 방법 |
|---|---|---|---|
| 과정 | GitHub에 드러나는 고민·개발·홍보의 기록 | 홍보 시도 **전건**이 커밋으로 남는다. 실패·무반응도 남긴다. | `docs/marketing/experiment-log/` 파일 수, 커밋 이력 |
| 결과 | 완성도·유용성·**홍보 성과** | 실제 실무자에게 닿고, 받은 지적이 문서·제품에 반영된다 | 댓글·메시지 원문, 테스트 참여자 수, 반영 커밋 링크 |

**원칙: 숫자보다 내용.** 조회수·업보트는 채널 알고리즘에 좌우되지만, "이 항목이 실제로 가장 많이 빠진다"는 실무자의 한 문장은 제품을 바꾼다. 지표는 숫자와 원문을 함께 남긴다.

## 2. 타깃 — 누구에게, 무엇을 요청할 것인가

| 순위 | 대상 | 이 사람이 가진 것 | 우리가 요청할 것 |
|---|---|---|---|
| 1차 | **공기업·공공기관 실무자** (담당자 교체·인수인계 경험자) | 실제로 빠져서 곤란했던 항목, 조직 내 서식 관행 | "인수인계서에서 가장 자주 빠지는 항목" 1~3개 + 체크리스트 점검 |
| 2차 | **직장인 일반** (문서화·업무 이관 담당, 총무·기획·운영) | 인수인계를 주고받는 절차와 반발 지점 | 체크리스트 사용 후기, 표현·항목 지적 |
| 3차 | **IT·생산성 커뮤니티 사용자** (GeekNews, 디스콰이엇 등) | 구현·설계에 대한 냉정한 지적, 확산 | 시제품 사용 후 피드백, 기술적 허점 지적 |
| 4차 | **교내·지인** (한양대 수강생, 팀원 지인 중 실무자) | 즉시 응답, 반복 테스트 가능 | 1:1 사용 테스트, 스크린 녹화 동의 |

**타깃별로 메시지를 바꾼다.** 1차에는 "체크리스트 무료 공개", 3차에는 "어떻게 만들었고 무엇이 아직 안 되는가"가 먹힌다. 같은 글을 복사해 채널마다 붙이면 규정 위반이면서 반응도 없다.

## 5. `docs/marketing/` 폴더 구조

```
docs/
├── handover-checklist.md                  # 공개용 체크리스트 (2주차 산출물 겸 리드마그넷)
└── marketing/
    ├── promotion-strategy.md              # 이 문서
    ├── channel-copy-drafts.md             # 채널별 게시 문구 초안 (A~F)
    ├── experiment-log/
    │   ├── _template.md                   # 실험 로그 템플릿 (아래 §6)
    │   ├── index.md                       # 전체 실험 한눈에 보기 (표 한 줄 = 실험 한 건)
    │   ├── 2026-11-25-careerly.md         # 예: 채널·날짜별 파일 1개
    │   ├── 2026-12-02-geeknews-show.md
    │   └── ...
    └── feedback/
        ├── index.md                       # 받은 피드백 원문 목록 (출처·날짜·반영 여부)
        └── 2026-11-26-interview-01.md     # 1:1 인터뷰·테스트 기록 (익명 처리)
```

**파일 규칙**
- 실험 로그 파일명: `YYYY-MM-DD-채널.md` (같은 날 같은 채널 재시도 시 `-2` 접미)
- 피드백 파일: 개인 식별 정보 없이 `interview-01`처럼 번호로. 이름·소속·연락처는 저장소에 올리지 않는다.
- 커밋 메시지: `docs(marketing): 커리어리 게시 실험 기록` 처럼 **문서 영역 + 성격**이 드러나게.

## 6. 홍보 실험 로그 템플릿 (복사해서 사용)

### 6.1 개별 실험 파일 (`experiment-log/YYYY-MM-DD-채널.md`)

```markdown
# [채널명] 홍보 실험 — YYYY-MM-DD

## 1. 기본 정보
| 항목 | 내용 |
|---|---|
| 채널 | (예: 커리어리 커뮤니티) |
| 게시 일시 | YYYY-MM-DD HH:MM |
| 게시자 | (팀 계정 / 개인 계정) |
| 게시 위치 | (게시판·그룹명, 링크 URL) |
| 사용한 문구 | channel-copy-drafts.md 의 (A-1) — 실제 게시문은 아래 §2에 전문 보관 |
```

**"못 셈"을 하나 줄이는 방법.** 체크리스트 다운로드처럼 남의 페이지 안에서 일어나는 일은 우리가 셀 수 없지만, 데모 웹은 우리가 배포하는 페이지이므로 방문과 체험 횟수를 직접 셀 수 있습니다. 링크를 받은 사람이 들어와 꼬리질문 단계까지 가 본 횟수가 익명으로 쌓이면, 최종 평가에서 "실제로 얼마나 들어와 써 봤는가"를 정량 근거로 제시할 수 있습니다. 횟수만 세고 누가 했는지는 저장하지 않는 것이 전제입니다.

> **없는 수치를 만들지 않는다.** "조회수 약 500" 같은 추정치는 근거가 없으면 쓰지 않고, 대신 받은 문장을 그대로 남긴다. 이 저장소는 이미 "정직하게"를 문서 원칙으로 삼고 있다(`README.md` §3, §8).

## 8. 지킬 선 — 홍보에서 절대 하지 않을 것

| 금지 | 이유 |
|---|---|
| 회사명·브랜드·사내 시스템명 노출, 실제 인수인계서·메일·고객정보 사용 | 과제 조건이자 개발 원칙. 홍보물이 곧 공개 문서이므로 더 위험 |
| 회사 업무 시간에 회사 자원으로 홍보 | `README.md` §8 원칙 |
| 지인에게 업보트·댓글·추천 요청 | GeekNews·디스콰이엇 규정 위반. 계정 제재 위험 |
| "법적으로 문제없다"는 식의 단정 | 제품은 검토 보조. ③ 기능의 한계를 홍보 문구에서도 유지 |
| 같은 글 다채널 복사·반복 게시 | 규정 위반 + 반응 저하 |
| "공식 표준"이라는 표현 | 체크리스트는 우리 초안. 공개 표준은 **지향**이지 현재 상태가 아님 |
| 수업 과제·교수 피드백을 홍보 문구의 신뢰 근거로 쓰기 | 외부 독자에게 무의미하고, 학교 관련 표현은 확인 필요 |

**홍보 문구에 항상 들어갈 3요소:** ① 지금 상태(구현 전/시제품/MVP), ② 가상 자료로만 시연한다는 사실, ③ 무엇을 피드백받고 싶은지.
