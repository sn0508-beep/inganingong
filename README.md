## 1. 무엇을 만드는가

공기업 등 공공 조직에서 업무 담당자가 바뀔 때 쓰는 **인수인계서**를 돕는 AI 도구입니다.

| 구분 | 내용 |
|---|---|
| ① 작성 가이드라인 | 인수인계서를 처음 작성할 때 무엇을 어떤 순서로 담아야 하는지 안내 |
| ② 후임자 관점 꼬리질문 | 작성된 초안을 넣으면 AI가 후임자 입장에서 꼬리질문을 던져 빠진 내용을 끌어냄 |
| ③ 약관·법규 검토 | 인수인계 내용에서 사실과 다른 부분, 근거가 되는 공개 약관·법규 조항을 함께 제시 |

②의 결과물은 정리된 인수인계서와 **"아직 답하지 못한 질문 목록"** 입니다. ③은 법적 판단을 확정하는 기능이 아니라, 확인이 필요한 지점과 근거 조항을 짚어 주는 검토 보조입니다.

**이번 5주 범위에서 제외한 것:** 회사 메일 연동. 2026-11-11 회의에서 "인수인계서는 정해진 항목만 담고 있어 갑작스러운 변수나 현안을 반영하기 어렵다"는 문제 제기와 함께 메일 연동안이 나왔지만, 한 달 안에 구현하기에는 범위가 지나치게 커진다는 판단으로 이번 범위에서는 빼고 **확장 후보**로 남겼습니다.

## 2. 문제

**인수인계받는 사람은 아무것도 모르는 상태에서 시작합니다.** 그런데 인수인계서는 현임자 자신의 주관적 관점과 익숙한 맥락을 따라 쓰이기 쉬워, 현임자에게는 설명할 필요가 없어 보이는 전제(왜 이렇게 처리하는지, 누구에게 먼저 연락하는지, 어디서 자주 막히는지)가 문서에서 빠집니다.

- 인수인계서는 서식에 정해진 항목만 채우기 쉬워, 후임자가 실제로 막히는 지점(예외 상황, 연락처와 협조 체계, 시스템 접근, 반복되는 문제)이 빠진 채 넘어갑니다.
- 문서가 부실하면 후임자는 같은 시행착오를 처음부터 다시 겪습니다. 이때 필요한 것은 요약이 아니라 **후임자 눈높이에서 빠진 전제와 맥락을 끌어내는 꼬리질문**입니다. 그 질문이 없으면 항목은 다 채워져 있어도 후임자에게는 여전히 반쪽 문서입니다.
- 기존 도구는 이미 있는 문서를 검색하는 방식(사내 문서 RAG 챗봇 등)이거나 서식·문서 생성 중심이어서, **문서 자체가 부실한 문제**는 해결하지 못합니다.
- 공공 영역에서도 필요성은 확인됩니다. 군포시가 업무 인수인계 표준안을 마련해 운영하는 사례가 조사에서 확인되었습니다.

**기존 사내 인수인계 사이트와 무엇이 다른가**

공기업·공공기관 가운데는 사내 인수인계 사이트를 따로 두는 곳도 있습니다. 그러나 대부분은 현임자가 만든 파일과 필요한 서식을 올리고 내려받는 **'파일 교환 창구'** 역할에 머뭅니다. 문서를 주고받을 통로는 있어도, 그 문서가 후임자에게 충분한지 물어봐 주는 단계는 없습니다.

이 도구도 최종 결과물은 파일로 주고받습니다. 다만 단순히 파일을 전달하는 것이 아니라, **아무것도 모르는 제3자(AI)의 시각에서 실제로 필요한 내용을 물어보고 문서를 다듬어 주는 과정**을 거칩니다. 그 과정 자체가 이 도구의 핵심 가치입니다. 현임자가 "이건 당연해서 안 썼는데"라고 여겼던 전제가 질문을 통해 처음으로 꺼내지고, 후임자에게 가장 필요한 내용이 바로 거기서 나옵니다.

## 3. 핵심 방향은 어떻게 정해졌나

2026-11-11 21:45, Zoom 회의(19분 38초, 오홍걸·변지훈·최선주·이시내)에서 세 축으로 방향이 모였습니다.

- **꼬리질문 중심** — 후임자 관점의 질문을 던지는 부분을 제품의 중심에 둔다.
- **공기업 인수인계** — "공기업 전용 인수인계 템플릿 같은 느낌"으로 대상과 형태를 좁힌다.
- **약관·법규 검토 결합** — 인수인계 과정에서 틀린 부분을 짚어 주고, 공개 약관·법규까지 함께 검토한다.

회의 전에는 팀원마다 후보가 달랐습니다. 공개 약관·법령에서 근거 조항 찾기(이시내·변지훈), 공지문 쉬운 말 변환(오홍걸), 회의록에서 결정·담당·마감과 약속 이행률 추출(최선주)이 각각 나왔고, "규정 덩어리"와 "대화 덩어리"를 합치는 안을 거쳐 인수인계라는 한 지점으로 수렴했습니다. 이 과정은 `planning/ideas/`의 팀원별 탐색 기록과 회의 전사본에 그대로 남아 있습니다.

**차별점으로 보는 지점:** 문서를 대신 써 주는 도구가 아니라, 아무것도 모르는 제3자의 시선으로 빈틈을 드러내는 질문 설계(2장). 그리고 인수인계서 품질 체크리스트를 **오픈소스 표준으로 공개**하는 것 — 이는 팀원 탐색 기록에서 "평가 기준·체크리스트를 공개하는 전략이 차별화와 홍보 포인트가 된다"는 결론으로 정리된 방향입니다.

**기존 서비스 조사 현황(정직하게):** 2026년 11월, 1회 검색 기준으로 사내 문서 AI 위키·RAG 챗봇 구축 외주, 문서 생성·표준화 도구, 업무 인수인계 표준안 운영 사례 등 인접 서비스는 다수 확인했으나, **후임자 관점에서 대화로 빈틈을 캐묻는 제품은 그 검색 범위에서는 찾지 못했습니다.** 검색이 1회뿐이므로 "없다"고 단정하지 않으며, 추가 조사를 남은 과제로 두고 있습니다.

## 7. 아이디어 탐색 기록

이 프로젝트는 주제를 먼저 정하고 시작한 것이 아니라, 후보를 만들고 **버린 이유까지** 남기는 방식으로 좁혀 왔습니다. 팀원별 기록에는 적게는 몇 개에서 많게는 45개까지 후보와 탈락 사유가 정리되어 있습니다.

탐색 과정에서 팀이 합의해 온 탈락 기준(요약):

- 회사 내부 데이터가 있어야만 작동하는가
- 핵심이 생성형 AI가 아니라 규칙 기반 처리인가
- 5주 안에 불가능한 하드웨어·실시간 처리가 필요한가
- 새 앱 설치나 행동 변화를 요구하는가
- ChatGPT·NotebookLM에 파일을 올리면 바로 되는 일인가
- 대기업·정부·공모전 수상작이 이미 하고 있는가
- 제품을 사는 사람의 이해관계와 충돌하지 않는가

이 기준으로 탈락한 예: 계량기-고객 매칭 검증(내부 고객 데이터 필요), 소상공인 전기요금 진단(대기업·공공기관·공모전 수상작 존재), 회의록 실행 추적(기존 협업 도구와 중복). 후보마다 "검색 전 후보 / 조건부 생존 / 탈락" 같은 상태를 함께 표시해 두었습니다.

## 9. 웹 프로토타입 (v0.1) — 2026-11-18

기획만 있던 상태에서, 회의에서 정한 세 축을 **눌러 볼 수 있는 화면**으로 옮겼습니다. API 키 없이, 인터넷 없이도 그 자리에서 돌아갑니다. 화면 흐름과 구현은 이시내(@sn0508-beep)가 맡았습니다.

**실행**

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python run.py            # http://127.0.0.1:8000
python -m pytest tests   # 자동 테스트
```

**화면 4단계**

| 단계 | 하는 일 |
| --- | --- |
| 1. 시작 | `.hwp` `.hwpx` `.docx` `.pdf` `.txt` 업로드 또는 붙여넣기 · 공기업 인수인계서 표준 12항목 틀로 시작 · 개인정보 가림 미리보기 |
| 2. 빈틈 점검 | 12개 항목 커버리지 표시, 빈 곳과 모호한 표현을 겨냥한 후임자 관점 질문, 답변 입력·건너뜀 추적 |
| 3. 약관·규정 근거 | 내장 기본공급약관(또는 올린 PDF)에서 초안 문장별 근거 후보 조문을 `조문 번호 · 쪽수 · 발췌`로 표시 |
| 4. 내보내기 | 정리된 인수인계서 + **아직 답하지 못한 질문 목록**을 `.md` / `.txt`로 내려받기 |

**설계에서 신경 쓴 것**

- **LLM 없이도 완결** — 질문 생성은 항목별 신호(마감일·연락 수단·판단 기준 등)를 찾아 묻는 규칙 기반이라, 데모 모드에서 전부 동작합니다. LLM은 질문을 더하는 보조이며 실패하면 규칙 결과만 남습니다.
- **약관은 "올리면 색인"** — 기본공급약관은 예시일 뿐이고, 어떤 규정 PDF든 올리면 그 자리에서 조문·쪽수를 파싱해 같은 방식으로 찾습니다.
- **억지로 붙이지 않기** — 근거가 약하면 신뢰도 `낮음`으로 표시하고, 화면·문서 모두에 "법적 판단이 아니라 확인 보조"라고 적었습니다.
- **가린 뒤에 보내기** — 전화번호·이메일·주민등록번호를 가린 사본만 LLM으로 갑니다. 원문은 화면과 내보내기에 그대로 남습니다.

**검증 요약** (자세한 내용은 [`docs/prototype-v0.1.md`](docs/prototype-v0.1.md))

- 형식별 추출: `.hwpx` 631자 · `.docx` 684자 · `.pdf` 672자 · `.hwp`(실제 한글 파일) 1,599자
- 내장 기본공급약관: 136쪽 → 조문 107개 색인, `요금 이의신청` 문장 → `제74조의2 · 59쪽`
